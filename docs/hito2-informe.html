Recorrido: POST /api/analyses (petición → base de datos)

  1. Transporte: el route handler de app/api/analyses/route.ts recibe el JSON y valida el cuerpo (URL, formato, siteId opcional, frameworkIds) con contratos Zod de lib/contracts.ts. Si falla → 400 VALIDACION, sin llegar a la BD.
  2. Servicio: analyses.service.ts genera el id PS-XXXXXX (alfabeto sin caracteres ambiguos), ejecuta el motor real sobre la URL (con las guardas anti-SSRF del Hito 1) y arma el payload completo (hallazgos, evidencias, plan de acción).
  3. Repositorio: analyses.repository.ts llama a Prisma (create) — si el siteId no existe, la FK lo impide: el servicio traduce P2003 → 400 VALIDACION; si el id colisiona, reintenta con otro id (P2002 → nuevo intento, hasta 5 veces).
  4. Base de datos: PostgreSQL almacena la fila en analyses (score, riskLevel nullable, payload JSON, relación con sites).
  5. Respuesta: 201 con el análisis completo en el mismo formato que consume el informe del frontend (idéntico al formato localStorage: el informe y el historial no distinguen el origen).

Cualquier error lanzado por las capas internas es capturado en el handler y convertido en ApiError: salida siempre JSON uniforme, códigos HTTP correctos, nada de fugas internas.

4 · Modelo de datos y base real (requisito B4)

Modelo Prisma

model Site {
  id        String   @id @default(cuid())
  url       String   @unique
  nombre    String?
  notas     String?
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  analyses  Analysis[]
  @@map("sites")
}

model Analysis {
  id         String   @id            // formato PS-XXXXXX, asignado por el servicio
  url        String
  score      Int                     // 0..100
  riskLevel  String?                 // "bajo"|"medio"|"alto"|"critico" — puede ser null (honesto)
  payload    Json                    // análisis completo validado por Zod
  notas      String?
  revisado   Boolean  @default(false)
  siteId     String?
  site       Site?    @relation(fields: [siteId], references: [id], onDelete: Restrict)
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt
  @@index([createdAt(sort: Desc)]) @@index([siteId]) @@map("analyses")
}

Decisiones del modelo

  • id de sites = cuid: aleatorio y seguro de adivinar; generado por Prisma.
  • id de analyses = PS-XXXXXX: conserva el formato que el motor ya usaba en el Hito 1 para que historial e informe funcionen igual con datos locales o de la BD. El id lo asigna el servicio (no la base) y reintenta ante colisión.
  • FK siteId → sites.id con onDelete: Restrict: es imposible borrar un sitio con análisis asociados — la API responde 409 con code: "CONFLICTO_FK" y una pista para revisar el análisis antes de borrar. Protege la integridad del historial.
  • riskLevel nullable: si el insuficiente nivel de evidencia no permite clasificar riesgo, se guarda null en vez de inventar categorías.
  • payload JSON íntegro: conservamos el informe completo (hallazgos, evidencias, plan de acción) tal como lo consume el front, evitado cualquier transformación con pérdida de información.
  • Índices: createdAt desc (el historial pagina lo más reciente) y siteId (filtro por sitio).

7 · ¿Por qué un monolito modular y cómo se evalúa el código? (requisito A3)

Decisión estructural

PRIVACYOS es un monolito modular: un único despliegue (aplicación Next.js) con fronteras rígidas entre capas internas. Elegimos el punto medio entre "un solo archivo gigante" y "microservicios":

OpciónProsContras para un equipo de 3
Monolito anárquicorápido de empezarcódigo acoplado; imposible probar por capas; nos frenaría después
Monolito modular (elegido)despliegue simple + capas con fronteras + testeable caja negrarequiere disciplina en imports (documentada en README)
Microserviciosescalado por servicio3 repos/despliegues, CORS, versionado multi; sobrevisión total hoy

Escenario de revisión de diseño (cómo probarías el código)

En una corrección de diseño pedimos: «Implementa este endpoint nuevo: GET /api/sites/{id}/informe que devuelva el último análisis del sitio». Un revisor puede verificar, en menos de 15 minutos:

  1. Dónde cae el cambio — verificar que la lógica vive en analyses.service.ts y analyses.repository.ts, no en el route handler. La firma de las capas lo dice sola.
  2. Contrato primero — verificar que se documenta en docs/api.md antes de codear (como hicimos con todo el CRUD).
  3. Códigos HTTP — verificar que sitio inexistente da 404 y que un sitio con historial vacío da 200 con lista vacía. La envolvente de error y test-crud.mjs lo cubren.
  4. Prueba de regresión — verificar que se agrega el caso a scripts/test-crud.mjs en el mismo commit.

Las fronteras hacen que la revisión sean preguntas pequeñas y verificables, no debates de estilo.

8 · Asistente de IA explicativo: propuesta elegida, guardas y honestidad

Guardas anti-invención implementadas

  • Prompt de sistema de 8 reglas: máximo 3 frases; explica términos técnicos con lenguaje simple; usa solo la evidencia del JSON; si no está, lo declara; nunca afirma cumplimiento o incumplimiento legal; cierra con una acción concreta; marca la respuesta como «no es asesoría legal»; llama a revisión humana si el usuario lo necesita.
  • Claude de contexto: solo JSON automáticamente recortado (hallazgos + score + riesgos), no el HTML crudo; brevedad reforzada al final del turno del usuario (≤ 60 palabras).
  • Feature flag server-side: sin ASSISTANT_ENABLED=1, la ruta no existe para el mundo (503 documentado).
  • Llave solo en servidor (GEMINI_API_KEY nunca viaja al navegador) y códigos 502/503 con mensaje amable y contacto si la IA no está disponible — la app sigue funcionando sin el asistente.
  • Fallback de modelos (primario → alternativo → terciario, 30 s de timeout cada uno), de forma que la saturación del proveedor degrade con gracia.

Dictado por voz

El widget acepta dictado con la Web Speech API nativa del navegador (es-CL): sin proveedores externos, sin costos y sin datos de voz que salgan del dispositivo. El texto dictado va a la caja como si fuese tipeado, con botón de envío propio; si el navegador no soporta la API, el control simplemente no aparece (degradación limpia).

«Entrenar la IA»: una distinción honesta

Entrenar ≠ integrar. Esta iteración entrena la conducta del modelo, no sus pesos: le damos reglas de sistema, contexto cerrado al JSON del informe, tono, brevedad y guardas — la conducta se ajusta por instrumentación, sin tocar los pesos. Entrenar los pesos (fine-tuning, p. ej. LoRA) es la vía si el curso lo exige en su momento: es técnicamente posible pero requiere infraestructura de GPU que no está disponible hoy en el equipo; dejamos documentada la distinción para que la evaluación vea qué se hizo y qué queda como hoja de ruta. Ver §8, opción D.
